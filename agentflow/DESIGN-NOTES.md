# AgentFlow — Design notes

File này **không bao giờ được load lúc runtime** (hệ số token = 0). Nó giữ *vì sao* thiết kế như vậy, để prompt runtime chỉ cần giữ *làm gì*. `/agentflow:learn` đọc §Non-goals làm gate trước khi sửa plugin.

## Mục tiêu

1. Agent hoàn thành ticket trên GitHub Projects board **tới cổng của con người** (review/merge, QC tay, PO duyệt scope) — không hơn.
2. **Chi phí token thấp, đoán trước được**: prompt ngắn, đọc ít, đọc đúng lúc; subagent mỗi ticket để session chính không phình.
3. **Một plugin cho nhiều project**: mọi thứ khác nhau giữa project (tên cột, label, branch, lệnh check) nằm trong `agentflow.yaml`; plugin chỉ giữ ngữ nghĩa.
4. **Tự cải thiện có kiểm soát**: friction được ghi journal tự động, bài học chỉ vào plugin sau khi người duyệt diff.

## Quyết định chính và lý do

| Quyết định | Lý do | Đánh đổi chấp nhận |
|---|---|---|
| **Ba vai: PO (lệnh) → SA → DEV kiêm automation tester; bỏ QC agent** (người dùng chọn 2026-11-11, thay bản bốn vai PO → SA → QC → DEV cùng ngày) | QC agent phải học lại UI, build lại app và đọc lại context mà DEV vừa có (#36: ~376k token, 72 phút); mỗi QC ❌ là thêm một lượt DEV + SA Opus. DEV đã build app, biết màn hình và id nên viết + chạy flow rẻ nhất, và sửa ngay trong cùng context khi flow fail. Ticket bớt 2 spawn Opus (QC plan + QC verify, ~27.7k ký tự prompt mỗi spawn): happy path còn SA design + DEV + SA review ≈ 81k ký tự thay vì ≈ 130k | Mất người kiểm độc lập ở bước test. Bù: SA lập rủi ro + test case từ yêu cầu trước khi có code (DEV không tự chọn cái mình test), SA review soát flow có assert đúng AC và danh sách Kiểm chứng lại, mục QC tay cho người. Lượt DEV dài hơn (chờ pipeline, vòng sửa): `maxTurns` 300 |
| **SA thiết kế ở Ready (giải pháp + rủi ro + test case), review ở In Review** (người dùng chọn REVIEWER → SA; rủi ro + test case do SA lập trước, DEV chốt danh sách kiểm chứng lại theo diff thật) | Người chọn giải pháp cũng là người soát code có đúng giải pháp không: tiêu chí review khách quan hơn ("lệch thiết kế mà không có lý do"), DEV biết trước điều SA sẽ soát. Rủi ro và test case viết từ yêu cầu + vùng code dùng chung, trước khi có code, để bắt chỗ DEV hiểu sai AC. DoR ở SA; SA hỏi PO thì **không** gắn `labels.agent`, nên `/task #n` vẫn sửa được ticket. Thiết kế nằm ở comment `[AF:SA] design`, không trong body: body là của PO | Thiết kế ≤ 60 dòng. DEV được lệch khi chạm code thật nhưng phải ghi "Lệch thiết kế" + lý do; lệch làm đổi AC thì hỏi PO. PO sửa AC sau thiết kế ⇒ `/task` gỡ `labels.agent` để SA thiết kế lại |
| **DEV merge lên staging và tự chạy flow liên quan; tối đa `run.max_test_rounds` (3) vòng sửa; hết vòng ghi lỗi block lên issue** (người dùng chọn) | Vòng "flow fail → gắn id / sửa code → deploy lại → chạy lại" rẻ nhất khi nằm trong một context. Trần vòng để lượt không chạy vô hạn; lỗi block ghi từng TC (bước, kỳ vọng/thực tế, bằng chứng, đã thử gì, nghi vấn `file:line`) để người quyết mà không phải tái hiện lại. Chỉ chạy flow của ticket + flow có sẵn đi qua phần diff chạm; cả suite khi diff chạm phần dùng chung. Lỗi hạ tầng, ticket khác không tính vòng | Code chưa qua review đã lên staging: có thể làm hỏng flow của ticket khác trong lúc chờ — chấp nhận, trước đây staging cũng giữ code chưa qua QC. Vòng đếm trong lượt, không ghi vào state: DEV chết giữa chừng thì lượt sau đếm lại, trần spawn của dispatch chặn vòng lặp |
| **SA review sau khi flow pass trên staging; ✅ còn mục QC tay → In QC + `qc_manual`, không → SA undraft → Ready to Merge** (người dùng chọn) | SA chỉ đọc code đã chạy đúng, không tốn vòng review cho code còn hỏng. `test_sha` = head đã test: head mới chưa test ⇒ SA ❌ ngay, không đọc code, không tính round (spawn rẻ); DEV chạy §7 theo `head ≠ test_sha`, không theo "có push hay không", nên không ghi `test_sha` cho head chưa chạy flow. QC người chỉ khi có case không tự động được | Hook cho SA undraft, DEV vẫn không. SA không sửa file, không push, không đổi git (bỏ `Edit` khỏi tools, hook chặn): conflict staging chuyển sang DEV, người hiểu code nhất |
| **Chờ deploy server/web bằng `agentflow-board checks --wait 4` ngay trong lượt DEV; `staging.skip_checks` bỏ qua release mobile; flow mobile chạy trên emulator với bản build trỏ staging (`surfaces.<key>.install`)** (người dùng chọn không chờ release mobile) | Release mobile (TestFlight, Firebase) mất hàng chục phút mà flow không cần: emulator chạy bản build trỏ server staging. Mỗi lệnh chờ ≤ 4 phút để prompt cache (TTL 5 phút) còn ấm: chờ 30 phút tốn ~8 lần đọc cache thay vì ghi lại cả context, rẻ hơn spawn lại một DEV phải đọc lại ticket. Chờ khi diff kể từ `test_sha` chạm code server/web, kể cả merge `Already up to date` (DEV chết lúc đang chờ thì lượt sau vẫn chờ). Timeout tính trong lượt, không từ `deploy_at` cũ. Bash `timeout: 300000` vì mặc định 2 phút cắt lệnh chờ và `checks` chỉ in kết quả ở cuối. Orchestrator không còn canh pipeline (bỏ §3b, SYS *pipeline-ok/redeploy/qc-auto-pass*, label `deploying`) | Slot song song bị giữ trong lúc chờ. Check nào là release mobile do repo khai bằng glob; khai thiếu thì DEV chờ tới khi job đó xong |
| **Không viết unit/mock test; kiểm chứng = automation chạy thật trên staging** (người dùng chọn) | Test có mock kiểm cái DEV hình dung, không kiểm hệ thống thật; flow trên staging bắt lỗi tích hợp, dữ liệu, cấu hình. Test có sẵn của repo vẫn phải xanh; `CLAUDE.md` bắt buộc unit thì theo repo; SA ❌ unit/mock test mới không được yêu cầu | Logic thuần không có lưới an toàn nhanh; flow chậm hơn unit. Case API trên surface không có `e2e_dir` chỉ kiểm bằng `curl`, không chạy lại được ⇒ vào "Đề xuất kiểm chứng thêm" |
| **Ảnh UI chỉ mở khi flow fail + một ảnh cuối mỗi AC UI; SA không mở ảnh** (người dùng chọn) | Mỗi ảnh ~1–1.5k token; xem mọi state × mọi lần chạy là phần lớn token của bước test UI | Lệch cảm quan ở state không mở ảnh có thể lọt: đưa vào "Đề xuất kiểm chứng thêm" hoặc QC tay |
| **PR có mục Kiểm chứng lại: QC tay (chặn merge) + Đề xuất kiểm chứng thêm (không chặn)** (người dùng chọn) | Người merge và QC người thấy ngay cái gì chưa tự động được và vùng regression nên xem (rủi ro SA nêu + phần diff chạm mà flow không phủ). Chỉ phần QC tay là cổng, để ticket tự động được hết đi thẳng tới Ready to Merge. Riêng rework sau khi QC người báo fail: QC tay luôn có mục xác nhận lại lỗi đã báo (người dùng chọn 2026-11-12), vì E2E cho thấy DEV tự bỏ mục QC tay khi flow đã phủ case | DEV phải giữ hai mục khớp lần chạy cuối; SA ❌ khi thiếu rủi ro của thiết kế |
| **PO không đọc code, ticket không có giải pháp kỹ thuật** (người dùng chọn 2026-11-11, thay quyết định đọc ≤ 5 file + Ghi chú kỹ thuật) | Ticket nói *cái gì và vì sao*; *làm thế nào* là việc của SA, người đọc code có chủ đích. Ghi chú kỹ thuật của PO hay neo DEV vào một giải pháp chưa được cân nhắc. PO nói bằng giải pháp ⇒ hỏi ngược nhu cầu; ràng buộc kinh doanh thật (pháp lý, hợp đồng, hạn chót) vẫn ghi | Size do PO ước theo phạm vi, SA kiểm lại lúc DoR. Lệnh `/task` dài hơn (trần 9.4k) vì thêm khung cố vấn và bảng chấm, nhưng mỗi ticket bớt tới 5 lần đọc file |
| **`references/engineering.md` dùng chung cho SA và DEV** | Một nguồn chuẩn kỹ thuật (kiến trúc theo tầng của repo, SOLID, pattern khi cần, bảo mật, hiệu năng, test) cho cả người thiết kế/soát lẫn người code, thay cho việc DEV đọc cả prompt REVIEWER để tự review. Luật của repo (`CLAUDE.md`, pattern sẵn có) luôn thắng | SA và DEV đọc thêm ~2.8k ký tự mỗi spawn; DEV bớt ~8.3k |
| **Giữ `schema: 5` cho bản 3.0** | Không đổi key bắt buộc nào của `agentflow.yaml`: `run.models.sa` mới, `run.models.reviewer` của config cũ vẫn được đọc; key state mới (`design`, `e2e`) là tuỳ chọn, thiếu = ticket cũ; `[AF:REVIEW]` cũ đọc như `[AF:SA]`; guard coi `agentflow:reviewer` là SA. Tăng schema buộc mọi repo chạy lại `/agentflow:init` (viết lại config, không migrate) trong khi foxygym đọc plugin thẳng từ working tree | Ticket đang chạy dở theo luồng cũ đi tiếp không cần thiết kế: SA review tự phán giải pháp, DEV `resume`/`rework` không bắt buộc thiết kế |
| **Stage ngữ nghĩa + map tên cột trong config** | Board thật của mỗi team đặt tên khác nhau; ép đổi tên board là rào cản cài đặt lớn nhất | Tên option là wire value — đổi tên trên GitHub UI mà không sửa yaml là hỏng routing; `doctor` bắt lỗi này |
| **Test trên staging trước review và merge** (`in_progress → staging → in_review → ready_to_merge`) | Test trên hệ thống đã deploy thật mới thấy lỗi tích hợp; master chỉ nhận code đã chạy đúng trên staging và qua review | Mọi repo phải có nhánh staging và pipeline (bắt buộc, một luồng để prompt không phải tả hai đường) |
| **Draft PR do DEV mở, chỉ SA ✅ (không còn QC tay) hoặc QC người pass mới undraft** | Giữ inline review + CI của PR ngay từ đầu; draft không merge được nên là chặn thật, không chỉ là quy ước. Feedback sau undraft đưa PR về draft | PR draft không gửi review request tự động cho tới khi undraft |
| **Staging merge dồn, không reset, không force-push** | Chạy song song được, giữ nguyên bất biến cấm force-push | Code chưa đạt của ticket khác vẫn nằm trên staging, staging lệch dần master, lỗi có thể đến từ ticket khác ⇒ DEV phải phân loại (lỗi block chỉ khi do chính ticket). Người tự reset khi cần; DEV thấy `contains: false` thì deploy lại |
| **DEV tự merge + giải conflict trên staging, từ worktree tạm `af-<n>-staging`** (2.x–3.0 sớm: REVIEWER/SA làm; người dùng chọn thay vì script) | Không thêm role; người viết code giải conflict đúng ý nhất. Hook: DEV chỉ push staging từ worktree staging, worktree đó chỉ push vào staging, không đưa staging vào nhánh ticket | Không chắc ⇒ `blocked` |
| **Chỉ merge PR branch → staging, không bao giờ ngược lại** | Merge ngược sẽ đưa code chưa đạt của ticket khác vào PR master | Conflict không trả về DEV được, phải giải ngay trên staging |
| **Xét check của head staging, không phải của `deploy_sha`** | Merge dồn + `concurrency: cancel-in-progress` làm build của SHA cũ bị huỷ dù head đã chứa nó | Ticket đợi lâu hơn khi có push liên tiếp |
| **Head không có check nào = pending** | Pipeline cần vài giây để đăng ký; dựa vào `timeout_min` để kết luận | Repo không có pipeline thì mỗi ticket mất trọn timeout rồi `blocked` — init + doctor cảnh báo |
| **Bỏ `surfaces.<key>.e2e_ci` và `qc: auto · manual · agent`** (3.0) | DEV luôn tự chạy flow liên quan trên staging, nên "CI xanh là đủ QC" không còn là một nhánh riêng; một luồng cho mọi surface | Key cũ chỉ còn cảnh báo trong doctor; CI chạy cả suite sau release vẫn là lưới thêm của repo |
| **Maestro trước cho test UI, mobile lẫn web; agent tự xem ảnh chụp để soát UI/UX** (người dùng chọn 2026-11-02) | Flow Maestro thao tác như người dùng (nhìn, chạm, gõ, đọc màn hình) nên kiểm đúng điều người dùng gặp; một framework cho cả mobile và web, YAML không cần dependency trong repo. DEV chụp và tự xem ảnh (khi fail, một ảnh cuối mỗi AC UI) để so với design và màn cùng loại: bố cục, chữ cắt/tràn, trạng thái, phản hồi thao tác. Không dùng `assertWithAI`/`assertNoDefectsWithAI` của Maestro: cần API key và gửi ảnh staging ra dịch vụ ngoài | Maestro web non hơn Playwright (giả lập network, dựng dữ liệu qua API): AC cần thứ đó thì dùng framework khác. Repo đã chọn framework khác trong `e2e_dir` thì theo repo. Máy chạy agent cần `maestro` và emulator/simulator; ảnh nằm ở `/tmp` của máy đó, verdict chỉ ghi tên ảnh |
| **Review ❌ mọi điểm chưa tối ưu** (người dùng chọn, chấp nhận tốn Opus) | Chất lượng giải pháp là tiêu chí cổng, không phải gợi ý. Từ 3.0 giải pháp được chốt ở thiết kế nên review chủ yếu đo độ lệch so với thiết kế và `engineering.md` | Nhiều vòng hơn. Giới hạn hội tụ: chỉ phán diff, không nêu điểm mới ở code đã qua review, không ép gu; escalate sau `max_review_rounds` |
| **Đếm round riêng: review 3 liên tiếp, QC người 2, vòng sửa test 3 trong một lượt DEV** | Review khắt khe không được ăn hết lượt của QC người; vòng test là sửa nhanh trong context, không phải verdict | Hai key state + ba key config |
| **QC người fail về `ready` + `qc_failed`, review ❌ về `in_progress`** (người dùng chọn) | Việc bị QC trả hiện rõ trên board; review ❌ là vòng nội bộ nhanh | Ready không còn chỉ là việc mới: DEV xếp hạng rework trước; DoR do SA kiểm trước khi thiết kế |
| **Chỉ PO đưa Backlog → Ready: tự kéo card, hoặc xác nhận trong `/agentflow:task` khi đạt cổng Ready** (người dùng chọn 2026-11-11) | Ưu tiên + scope là quyết định sản phẩm. PO vừa chốt spec trong session thì kéo card là bước thừa. Cổng Ready (AC phán được, Priority, Size không phải option cuối, Platform, assignee, milestone khi repo có milestone mở, không bị issue mở chặn, không phải issue cha) chặn trước để DEV không nhận việc rồi lại `needs_info`. `/do` gặp ticket Backlog chỉ đề nghị `/task #n`, không tự chuyển: một đường duy nhất qua cổng | Loop không tự lấy việc mới khi Ready trống. Cổng chặt hơn DoR của DEV (thêm Platform, assignee, milestone): PO muốn bỏ qua thì tự kéo card |
| **`/task` hỏi tới khi đủ checklist, tìm issue trùng, tách sub-issue** (người dùng chọn 2026-11-11; phần đọc code bị thay ngay hôm đó, xem dòng PO ở trên) | Ticket thiếu là nguồn `needs_info` và QC ❌ đắt nhất: hỏi PO thêm một lượt trong session rẻ hơn một vòng DEV → REVIEWER → staging. Checklist theo type và khía cạnh (đường lỗi + trạng thái, quyền, dữ liệu cũ, tracking/hiệu năng/bảo mật) thay cho trần số lượt; PO nói "xong" thì dừng, mục thiếu thành `Chưa rõ` và cổng không qua. Đọc ≤ 5 file để hỏi đúng chỗ và ước lượng Size, AC vẫn viết theo hành vi; điều thấy được ghi vào Ghi chú kỹ thuật (gợi ý) để DEV khỏi dò lại. Lựa chọn rời rạc qua AskUserQuestion với option thật của board/form, nội dung mở hỏi chữ. Việc lớn: issue cha ở Backlog mãi, sub-issue native qua cổng từng cái. Assignee mặc định là login của `gh` vì `/run` bỏ qua ticket Ready assign cho người khác. Quyết định Ready ghi ở phần sau của `[AF:SPEC] created`/`refined`, không thêm dòng đầu mới, để không phải tăng schema. Milestone đọc qua `agentflow-board milestones` (REST, có test) | Prompt `/task` dài hơn gấp đôi (trần 8.4k ký tự), nhưng chỉ load khi PO gọi, không vào spawn nào. Đọc code, Figma, ảnh tốn thêm token mỗi ticket. Chạy `/do` ngay sau Ready chiếm session của PO tới khi ticket dừng ở cổng người |
| **`/task`: 1 ticket, cha + sub-issue hay N ticket độc lập là PO chốt qua AskUserQuestion, không tự quyết** (người dùng chọn 2026-11-14, thay "đề xuất tách khi Size option cuối hoặc > 7 AC" và "PO kể nhiều việc → tạo từng cái") | Cách cắt việc quyết định thứ tự giao và cái gì release riêng — quyết định sản phẩm. Chỉ hỏi khi có dấu hiệu (nhiều việc, Size option cuối / > 7 AC, ≥ 2 lát giá trị giao riêng được) để ticket nhỏ không thêm lượt hỏi; preview tiêu đề + số AC để PO so trước khi chọn | Thêm một lượt hỏi cho việc lớn. Chọn 1 ticket dù Size option cuối thì ticket kẹt ở Backlog (cổng §6) tới khi PO hạ Size hoặc tách |
| **`/task` nắm sản phẩm qua tài liệu thiết kế (`design.repo`), PO vẫn là nguồn yêu cầu; ticket chỉ dùng ngôn ngữ sản phẩm, dẫn tài liệu khi cần** (người dùng chọn 2026-11-14) | Expert PO hỏi đúng chỗ khi biết màn, luồng, luật, thuật ngữ đang có — không phải hỏi PO điều tài liệu đã nói. ## Non-goals (bất biến — `/learn` phải DỪNG nếu bài học đụng vào)

- **Agent không bao giờ merge PR**, không approve PR, không force-push, không push vào nhánh `git.protected`, không chạy/dispatch workflow (ở nhiều repo chạy workflow là deploy), không xoá repo hay package (token có full scope nên GitHub không chặn hộ). Hook chặn cả sáu. Push thường vào `staging.branch` là ngoại lệ duy nhất, chỉ DEV làm, từ worktree staging — hook kiểm cả role và worktree.
- **Agent không bao giờ chuyển ticket ra khỏi `backlog`** khi chưa có xác nhận tường minh của người trong session.
- **Agent không bao giờ chuyển ticket ra khỏi `ready_to_merge`** trừ hai trường hợp: PR đã merge (→ `done`) hoặc có feedback của người trên PR (→ `in_progress`, PR về draft).
- **Agent không bao giờ sửa hay in nội dung path trong `forbidden`** (mặc định: secret).
- **Không message bus, không database ngoài GitHub.** Trạng thái = Status trên board + label + state block + comment.
- **Không thêm field bắt buộc vào state block** khi chưa có consumer đọc nó.
- **Không có bản sao thứ hai của một fact** trong prompt runtime — một nơi gốc, chỗ khác trỏ về.

## Giới hạn đã biết

- Pipeline báo xanh trước khi deploy xong thì flow có thể chạy trên bản cũ: plugin chỉ thấy check, không thấy phiên bản đang chạy trên staging. Giảm nhẹ: chờ tối thiểu 2 phút từ `deploy_at`, init yêu cầu check bao trùm bước deploy.
- Guard không thấy thứ chỉ lộ ra lúc chạy: script được ghi rồi chạy ở lệnh sau mà nội dung tạo động, `make deploy`, `npm run x`, payload decode (`base64 -d | sh`), `grep -r` trên thư mục con có file secret (guard chỉ soát file secret ở ngay thư mục được chỉ định), tên file ghép động (`cat "$(printf .%s env)"`). Agent cố tình lách vẫn lách được; guard nhắm vào agent bình thường hoặc bị văn bản trong issue dẫn dắt. Đọc file script chỉ áp luật git/gh, không áp luật path secret.
- Guard coi `source .env` là được phép: giá trị vào env của lệnh, không vào transcript; lệnh in env bị chặn riêng.
- `disableAllHooks` trong settings do người đặt thì hook không chạy; subagent không sửa được file đó, session chính bị chặn khi ghi key này.
- Projects v2 không có compare-and-swap; compare-then-write chỉ thu hẹp cửa sổ race. So sánh Status đặt **trước** khi ghi state/comment/label: eval 2026-10-31 cho thấy so sánh ở cuối làm abort để lại state block và label nửa vời. **Một loop session cho mỗi repo** là giả định vận hành.
- Projects v2 không có history API; metrics dựng lại từ timestamp của comment `[AF:…]`.
- `updateProjectV2Field` thay toàn bộ option; `ProjectV2SingleSelectFieldOptionInput.id` (introspect 2026-10-30) cho phép giữ option sẵn có ⇒ `status-apply` luôn truyền id của option cũ, chỉ option bị bỏ mới mất Status của card (cần `--allow-drop`). Hành vi giữ id mới verify qua schema, chưa verify end-to-end trên board có card — `status-plan` luôn chạy trước.
- Người kéo card qua SA ❌ (override) mà không gỡ `changes_requested` thì mỗi lượt loop đưa ticket về DEV: override thì gỡ label.
- Guard không theo được nhánh tạo gián tiếp từ staging (vd tên nhánh khác trỏ vào commit merge của staging rồi merge vào nhánh ticket): chặn các đường trực tiếp (merge/reset/restore/push `origin/staging:<nhánh>`, `update-ref`, `read-tree`, `git branch` ghi), phần còn lại là luật của prompt.
- Mention chính mình không tạo notification — mention người khác (`people.*`) mới có tác dụng.
